# COAGO — Product Brief

สถานะ: ร่างขอบเขตผลิตภัณฑ์สำหรับพัฒนา (Draft)
ที่มา: เป้าหมายที่เจ้าของโครงการระบุในบทสนทนา และขอบเขตรุ่นแรกที่ร่างร่วมกัน
ชื่อโครงการ: COAGO
Repository: petchsnowa/coago-ride

เอกสารนี้กำหนดปัญหา ผู้ใช้ และพฤติกรรมของแอป ข้อเสนอรายละเอียดด้านล่างยังปรับได้ ไม่ใช่ approved architecture และไม่ใช่หลักฐานว่าฟีเจอร์ได้รับการพัฒนาหรือทดสอบแล้ว

## 1. ปัญหาและเป้าหมาย

COAGO ตั้งใจแก้ปัญหาคนที่ไม่มีรถและต้องการเดินทางไปต่างจังหวัด ขณะเดียวกันคนที่มีรถกำลังเดินทางและมีที่นั่งว่างสามารถเปิดรับผู้ร่วมทางได้

เป้าหมายคือให้ทั้งสองฝ่ายค้นหากัน ดูรายละเอียดเส้นทาง และนัดหมายร่วมเดินทางได้สะดวกขึ้น โดยผู้ขับขี่มีแผนเดินทางอยู่แล้ว

## 2. ผู้ใช้หลัก

- ผู้โดยสาร: คนที่ต้องการเดินทางข้ามจังหวัดและกำลังหารถร่วมเดินทาง
- ผู้ขับขี่: คนที่มีแผนเดินทางอยู่แล้วและต้องการเปิดรับผู้ร่วมทางตามจำนวนที่นั่งว่าง
- ผู้ดูแล: ผู้รับรายงานปัญหาและตรวจสอบตามสิทธิ์ที่กำหนด

บัญชีเดียวสามารถเป็นผู้ขับขี่หรือผู้โดยสารในแต่ละเที่ยวได้

## 3. เส้นทางใช้งานหลักของรุ่นแรก

1. ผู้ขับขี่ประกาศเที่ยว ระบุต้นทาง ปลายทาง วันเวลา จุดนัดพบ จำนวนที่นั่งว่าง และรายละเอียดรถ
2. ผู้โดยสารค้นหาจากจังหวัดต้นทาง จังหวัดปลายทาง และวันเดินทาง
3. ผู้โดยสารดูรายละเอียดเที่ยวและส่งคำขอร่วมเดินทาง
4. ผู้ขับขี่รับหรือปฏิเสธคำขอ
5. ทั้งสองฝ่ายดูสถานะและรายละเอียดการนัดหมายของเที่ยวที่ตอบรับแล้ว
6. ผู้ขับขี่ปิดเที่ยวเมื่อเดินทางเสร็จ หรือยกเลิกพร้อมระบุเหตุผล

## 4. ข้อมูลประกาศเดินทาง

- จังหวัดและจุดเริ่มเดินทาง
- จังหวัดและจุดหมายปลายทาง
- วันและเวลาออกเดินทาง
- จุดรับและจุดส่งที่ตกลงได้
- จำนวนที่นั่งว่าง
- ยี่ห้อ รุ่น สีรถ และข้อจำกัดสัมภาระ
- เงื่อนไขการร่วมเดินทาง
- เงินร่วมค่าเดินทางต่อคน หากมี โดยแสดงก่อนส่งคำขอ

ข้อมูลติดต่อส่วนตัวและทะเบียนรถฉบับเต็มควรแสดงเฉพาะคู่เดินทางที่ตอบรับแล้วตามความจำเป็น การอนุญาตให้เข้าถึงต้องตรวจที่ API ไม่ใช่ซ่อนในหน้าจอเพียงอย่างเดียว

## 5. กติกาคำขอและที่นั่ง

- คำขอมีสถานะ รอตอบรับ ตอบรับแล้ว ปฏิเสธ หรือยกเลิก
- คำขอที่รอตอบรับยังไม่ถือว่าได้ที่นั่ง
- เมื่อตอบรับ ระบบต้องตรวจและลดจำนวนที่นั่งอย่างถูกต้อง ป้องกันการรับเกินจำนวนแม้มีคำขอเข้าพร้อมกัน
- เมื่อยกเลิกคำขอที่ตอบรับแล้ว ต้องคืนที่นั่งตามสถานะเที่ยว และไม่คืนซ้ำจากการเรียกคำสั่งเดิมซ้ำ
- ผู้ใช้ส่งคำขอซ้ำในเที่ยวเดียวกันหรือจองเที่ยวของตนเองไม่ได้
- เที่ยวที่เต็ม ยกเลิก หรือออกเดินทางแล้วต้องไม่เปิดรับคำขอใหม่
- ผู้ใช้ดูและจัดการได้เฉพาะข้อมูลที่ตนมีสิทธิ์เข้าถึง
- รายละเอียดจำนวนที่นั่งต่อคำขอ เงื่อนไขการส่งคำขอใหม่หลังยกเลิก และเวลาตัดรอบยกเลิก ต้องกำหนดก่อนพัฒนาพฤติกรรมส่วนนั้น

## 6. หน้าจอรุ่นแรก

- หน้าแรกและค้นหาเที่ยว
- ผลการค้นหาและรายละเอียดเที่ยว
- สร้างและแก้ไขประกาศเดินทาง
- คำขอร่วมเดินทางสำหรับผู้ขับขี่
- รายการเดินทางและคำขอของฉัน
- สมัครสมาชิก เข้าสู่ระบบ และโปรไฟล์
- รายงานปัญหาหรือผู้ใช้ให้ผู้ดูแลตรวจสอบ

## 7. ลำดับการพัฒนา

### Phase 1 — วางฐานระบบ

อ้างแนวทางใน [AGENTS.md](../AGENTS.md):

- TypeScript monorepo
- React/Vite frontend พร้อมหน้าเริ่มต้นและสถานะ API
- Hono API บน Cloudflare Workers
- Shared packages แยก browser-safe contracts ออกจาก server database code
- Drizzle schema และ versioned migrations สำหรับ PostgreSQL/PostGIS ตามข้อกำหนดที่ยืนยันแล้ว
- Environment examples ที่ไม่มีข้อมูลลับ
- Liveness/readiness health checks
- CI และ initial automated tests
- README สำหรับติดตั้ง รัน และตรวจสอบ
- ตรวจ PostgreSQL/PostGIS และ Workers connectivity ตามสภาพแวดล้อมที่เข้าถึงได้ พร้อมรายงานข้อจำกัด

Phase 1 ยังไม่รวมการทำเส้นทางจองทั้งหมด และห้าม deploy production resources หรือรัน production migrations

### Phase 2 — ทำเส้นทางใช้งานหลัก

- บัญชีผู้ใช้และการควบคุมสิทธิ์
- ประกาศและค้นหาเที่ยว
- ส่งคำขอ ตอบรับ ปฏิเสธ และยกเลิก
- จัดการที่นั่งและสถานะเที่ยว
- ทดสอบสิทธิ์ ความสอดคล้องของสถานะ และการตอบรับพร้อมกัน

### Phase 3 — เตรียมทดลองใช้

- การแจ้งเตือน
- เครื่องมือผู้ดูแลและการรายงานปัญหา
- กำหนดวิธียืนยันผู้ใช้และเงื่อนไขการใช้บริการก่อนเปิดให้บุคคลทั่วไป
- ทดลองด้วยกลุ่มจำกัดตามแผนที่กำหนด

## 8. เลื่อนไปหลังรุ่นแรก

- ระบบชำระเงินในแอป
- แชตในแอป
- ติดตามตำแหน่งรถสด
- จับคู่เส้นทางอัตโนมัติ

ห้ามเพิ่มรายการเหล่านี้โดยอัตโนมัติระหว่างทำ Phase 1

## 9. เกณฑ์สำเร็จ

### ฐานระบบ Phase 1

ติดตั้ง dependencies จาก lockfile ได้ รัน development frontend/API ได้ และมีหลักฐาน lint, typecheck, tests, build, migrations และการตรวจฐานข้อมูลตามที่ทำได้จริง ต้องแยกผล mock, PostgreSQL จริง, local Workers runtime และ remote Workers connectivity

### แอปรุ่นแรกที่มีเส้นทางใช้งานหลัก

- ผู้ขับขี่ประกาศเที่ยวได้
- ผู้โดยสารค้นหาและส่งคำขอร่วมทางได้
- ผู้ขับขี่ตอบรับหรือปฏิเสธได้
- ทั้งสองฝ่ายเห็นสถานะตรงกัน
- ระบบไม่รับผู้โดยสารเกินที่นั่ง แม้มีการตอบรับพร้อมกัน
- การยกเลิกปรับสถานะและจำนวนที่นั่งถูกต้อง
- ผู้ไม่มีสิทธิ์เข้าถึงข้อมูลส่วนตัวหรือแก้ไขเที่ยวของผู้อื่นไม่ได้

ทดสอบด้วยบัญชีและข้อมูลตัวอย่างก่อนเปิดใช้งานจริง

## 10. ข้อเลือกที่ยังต้องกำหนด

- วิธีสมัครและเข้าสู่ระบบ
- วิธีและระดับการยืนยันผู้ใช้/ผู้ขับขี่
- ผู้ให้บริการฐานข้อมูลและรุ่น PostgreSQL/PostGIS
- วิธีเชื่อม Workers กับฐานข้อมูล
- Package manager และเวอร์ชัน runtime ที่รองรับ
- หนึ่งคำขอจองได้กี่ที่นั่ง
- กติกาแก้ไขเที่ยวที่มีผู้ตอบรับแล้ว การยกเลิก และการส่งคำขอใหม่
- วิธีระบุและชำระเงินร่วมค่าเดินทางนอกแอป หากมี
- การแจ้งเตือนและช่องทางติดต่อหลังตอบรับ
- นโยบายการแสดงข้อมูลส่วนตัวและสิทธิ์ของผู้ดูแล

บันทึกข้อเลือกทางเทคนิคใน docs/architecture.md และขอบเขตตรวจรับ Phase 1 ใน docs/phase-1.md เมื่อจัดทำจริง ไม่ถือว่าไฟล์เหล่านี้มีอยู่หรือได้รับอนุมัติจากการอ้างชื่อในเอกสารนี้
